# Architecture

Last reviewed: 2026-11-17. This is a map of current module ownership, not a roadmap. GitHub `main` is authoritative.

## Server

| Module | Owns |
|---|---|
| `app/main.py`, `app/api/` | FastAPI assembly and HTTP adapters: request validation, authentication dependencies, response/status mapping and route registration. Keep business rules out of route handlers. |
| `app/security/` | Web-session authentication, login middleware, cookies and security boundaries. |
| `app/services/` | Application-lifetime services and background-worker coordination. `app/worker.py` starts worker-owned jobs; `app/worker_schedule.py` (efficiency W1) is its table-driven scheduler: one thread runs the due entries (`daily_maintenance`, then `insights_refresh`, then `similar_precompute`) one at a time and keeps each last run in the store's `meta` under `schedule:<name>` (a run that returns `NOT_READY` is not recorded and is retried after the entry's `retry_seconds`); it imports no job module, so `/api/diagnostics/runtime` reads those times (`schedule`) without loading worker code; auto fill and the metrics save keep their own threads; `library_enrich.py` and `insights_refresh.py` coordinate their respective loops. `similar_precompute.py` (efficiency W2) is the worker's daily similar-artist precompute: it builds its own owned index for the run (synchronously, dropped afterwards, no identity pass), runs `discovery/search/similar_precompute.run_precompute` from the stored cursor with the worker's stop event, and owns the artist-network arguments shared with the artist page (`network_kwargs`), so the worker imports no route module; the web process starts no precompute loop. `discovery_schedule.py` (efficiency W3) is the worker's second scheduler, on its own thread (`worker-schedule-discovery`) so the long precompute cannot delay it: `discovery_lists` (hourly: `refresh_stale_lists` over personal, classics, deep dives, new releases and the listening profile, none while automatic refill is off) and `lens_lists` (hourly: `lens_service._due`, then `refresh_exclusive`); it reads the librarian's helpers by attribute and does not import the legacy server; the web process starts no list refresh loop. `worker_heartbeat.py` (efficiency C3) is the worker's liveness stamp: a thread rewrites `DATA_DIR/worker.heartbeat` every 30 s only while `worker-schedule` and `worker-schedule-discovery` are alive, and `python -m app.services.worker_heartbeat` (the compose worker healthcheck) exits 1 when the stamp is over 5 minutes old; the web healthcheck uses the public `/api/auth/status`. `owned_prefetch.py` (efficiency K3 part 1) is the worker's `owned_prefetch` entry: one artist and one album in turn from the owned library (newest additions first, then by listens), each run through the page routes' own `artist_page` and `album_sections` with a worker-built network, so the provider rows it stores are the ones a first view would store, under the same keys; it imports no route module. It is off unless `OWNED_PREFETCH_BUDGETS` names daily per-provider caps. `prefetch_state.py` holds its budgets, request counting (`Spend`: a request past a cap, or to a provider not named, is refused before it is sent), per-day spent counts, cursors and coverage in the knowledge store's `meta` (`prefetch:spent`, `prefetch:cursor`, `prefetch:coverage`), and is read without worker code by `/api/diagnostics/runtime` (`prefetch`). Part 2 (efficiency K3) adds the album page's Deezer tracklist hook (cap `deezer`), Apple Music / Wikipedia description hook (caps `apple` and `wikipedia`, both needed) and year hook, each given to the worker's network only when its providers are named; `album_page_sources.py` owns those namespaces' loaders (HTTP `get` injected), store keys, TTLs and the rule that a refused or failed request is never stored, and both `app/api/metadata.py` (wrapped in `LayeredCache`) and the prefetch (read and write on the metadata store, since the worker does not attach `persistent_metadata`) use it, so the rows match by construction (`tests/test_album_page_sources.py` checks it); it imports no route module. The same module also owns the album year (MusicBrainz request counted through the cap), album links and artist image loaders; `owned_prefetch.entity_extras` runs the links and the image outside the page builders. `runtime_metrics.py` holds the in-process counters (provider requests by provider and outcome class, gate waits, store opens and statements by verb; no URLs or identifiers), fed by a process-wide patch of `httpx.Client.send`/`AsyncClient.send` and `urllib.request.OpenerDirector.open` (`count_all_httpx`, installed at startup; `MeteredClient` is the same count without the patch), by the observer hooks in `integrations/provider_gate.py` and `intelligence/store/db.py`, and read at `GET /api/diagnostics/runtime` (`app/api/diagnostics.py`); the worker saves its snapshot to the store's `meta` every 5 minutes. `layered_cache.py` is the metadata routes' cache (efficiency P4): `LayeredCache` keeps a bounded LRU per namespace (2,000 entries by default), reads `persistent_metadata` when given a store key, and runs the caller's loader under single-flight, so concurrent identical requests make one provider call; the loader's `Loaded` answer sets its memory TTL (or none) and whether it is stored. With `max_stale` (efficiency K2, opt-in per call: album reviews, album links, the Apple album page address) a stored value past its TTL but inside its maximum staleness (70 days) is answered at once, kept in memory for at most 10 minutes, and refreshed by one background run of the same loader; ages come from `MetadataCache.get_with_age` through `persistent_metadata.read_with_age`, attached in `app/main.py`. `stale_refresh.py` (efficiency K2) runs those refreshes on its own two-thread pool, one per key, at most 32 pending (more are dropped and the stale value stays); a failed refresh writes nothing. K2 part 2 applies the same rule to the artist and album pages' provider rows in the discovery search cache (`discovery/search/cache.py::read_or_revalidate`: MusicBrainz artist lookup, studio albums and the seed artist's tags, Last.fm album lists, ListenBrainz and Last.fm top songs, Discogs styles, tracklists): a row past its TTL and under 10 times it (an empty answer: 1 h TTL, 10 h) is served and refreshed on `stale_refresh.DISCOVERY_REFRESHER`, a second pool of the same size, handed to the page network only by `app/api/search.py::artist_network_for`; the worker precompute and the search and genre pages keep today's expiry, and candidates' tag lookups are not served stale. The review outlets' own answers (`album-review-source`) use it directly from `app/api/metadata.py`, and an answer built from a stale input is never stored as fresh. The MusicBrainz year cache those routes import (`integrations/musicbrainz/album_year.py::year_cache`) is a separate LRU dict of 2,000 pairs, since `integrations/` does not import `app/`. |
| `discovery/` | Discovery policy and read models: candidate gathering, list construction/refresh, lenses, feedback (including `genre_block.py`, the blocked-genre rows and the selection-time and read-time exclusion, `artist_lean.py`, the More like this / Less like this rows whose boost, penalty and seed policy live in `recommendation_feedback.py`, and `artist_block.py`, which only lists and lifts the existing "Not this artist" rows, and `discovery_mode.py`, the Safer / Balanced / Deeper knobs that `selection_policy.py` and `lenses.py` read, and `star_seeds.py`, Navidrome stars as a decayed seed weight with its cached read, and `deep_dive_bridge.py`, pure: extra albums for a lens list from the stored Artist Deep Dives list (`items` plus the held-back `extra_items`), matched by genre family, called at read time from `lens_service.list_response` through `list_payload.build_lens_list_response(bridge=...)` and, for Personal, Classics and New releases, from `navidrome_server._bridge_deep_dives` through `build_cached_discovery_list_response(bridge=...)`; the switch lives in `settings/service.py`), taste-derived discovery inputs, `library_snapshot.py`, the Navidrome inventory reads and `AlbumInventorySnapshot`, the album inventory cached per process by scan marker with a 5-minute maximum age (efficiency P5, used by the album gaps path), `refresh_guard.py` (efficiency W3), one refresh per list across the web and worker processes: `run_exclusive` wraps each list refresh (scheduled, manual and read-triggered) in `intelligence.jobs.run_job` under job `discovery_list_refresh` with the list as scope (`lens_lists` for the lens lists), answers a busy list with the caller's existing busy answer, keeps a live run's `started_at` moving with a heartbeat (so the unfiltered `recover_stale` of other jobs cannot hand it to the other process), fails a run its process left running at that process's next start or once its heartbeat is 15 minutes old, and runs the refresh under its in-process lock only when the knowledge store is missing or unusable (it never creates a file), and `discovery/search/`'s owned-library index, query/ranking, paging and search events. |
| `scripts/discovery_mode_sweep.py` | Offline, no-network sweep of the discovery-mode knobs over frozen private inputs (a pickled lens-build input and a personal-list capture); prints aggregates only. Imports `discovery/` and `recommendation/replay.py`; nothing imports it. |
| `scripts/backup_stores.py` | Efficiency S2: online backup of every SQLite store under the data directory with `sqlite3.Connection.backup` (copies 0600 in a 0700 directory, integrity-checked, no `-wal`/`-shm`). Holds the explicit store list (settings/discovery, knowledge, owner state, metadata cache, provider gate, radio, artwork index, waveform peaks); `tests/test_backup_stores.py` checks it against the code that names each file. Restore steps: `docs/DEPLOYMENT.md`. Nothing imports it. |
| `scripts/store_size_report.py` | Efficiency S1 (report part): read-only row counts and bytes per table and index for each store in `backup_stores.STORES` (`dbstat` bytes when available, `n/a` otherwise), plus file, `-wal` and page sizes; markdown to stdout, optional `--json`. Opens stores without creating files beside them (`immutable=1` when no `-wal`; skips a `-wal` without `-shm`). Prints names and numbers only. `tests/test_store_size_report.py`. Nothing imports it. |
| `scripts/gate_spacing_check.py` | Efficiency R3 live check: starts the real worker and web app on one scratch data directory with a fake MusicBrainz and fake Navidrome, drives MusicBrainz-calling web routes while the worker's auto fill runs, and reports gaps between MusicBrainz slot starts, grants and arrivals (`analyze` is the pure, unit-tested part). A `sitecustomize.py` it writes into the scratch directory redirects `musicbrainz.org` to the fake and refuses every non-loopback host; nothing in the repo is auto-loaded and no provider is contacted. Run by hand; nothing imports it. |
| `scripts/efficiency_inventory.py` | Efficiency K1: against a running local instance, requests every route the artist and album pages use for each target in an operator-made targets file (kept outside the repo), once cold and then warm, strictly sequentially; attributes provider requests per request from `/api/diagnostics/runtime` and, with `--data-dir`, classes each miss from read-only cache-row reads (`mode=ro`). Output holds route labels, target indexes and aggregates only. Reuses `scripts/efficiency_baseline.py`'s client. `tests/test_efficiency_inventory.py`. Nothing imports it. |
| `recommendation/` | Recommendation-engine policy: candidate evaluation, scoring/diversity allocation, result shaping, and deterministic capture/replay and comparison tools. |
| `acquisition/` | Acquisition lifecycle and safety: request coordination, source selection/switching, tracking, recovery, completion, cleanup and verified import transactions. |
| `intelligence/` | Server V2 knowledge and enrichment domain: dedicated store/schema, jobs, MusicBrainz imports and enrichment, store access (`intelligence/store/db.py`: `ensure_store` migrates once at web and worker startup; request handlers use `open_readonly` for reads and `open_writer`, with no migration, for writes; the worker and scripts keep `open_store`), artwork index, taste/listening analysis, insights, graph/path building and API response builders. |
| `integrations/` | External-system boundaries and protocol clients (Navidrome, slskd, ListenBrainz, Last.fm, MusicBrainz, Discogs and radio). Own provider I/O, parsing and provider-specific transport behavior—not discovery policy. `integrations/provider_gate.py` is the shared provider gate: a dedicated SQLite file (`provider_gate.sqlite3`) holding per-provider slot reservations across web and worker (`reserve`, `penalize`, `snapshot`); callers take a `Lane` (`musicbrainz_lane()`): every MusicBrainz caller is routed: worker-side (`intelligence/musicbrainz/api_fill.py` `Paced`, `intelligence/insights/provider_runtime.py`, `set_fetchers.py`, R3 part 1) and web-side (`discovery/` callers, `integrations/musicbrainz/*`, `discovery/search/providers.py`, the MusicBrainz host of the artwork `HostPacer`, R3 part 2). `tests/test_musicbrainz_gate_boundary.py` fails for a module that names the MusicBrainz host without the gate; `tests/conftest.py` gives every test a private no-wait gate. |
| `settings/` | Configuration defaults, validation, settings persistence and generation/version helpers. `settings/persistence.py` caches decoded settings per process behind one read connection and re-reads when `PRAGMA data_version` changes, after a local write, or when the file or process changes (efficiency P1). |
| `navidrome_server.py` | Legacy compatibility and orchestration boundary still used by existing server callers. Do not add code; new behavior belongs in the appropriate package and this module may only shrink. |
| `static/`, `app/templates/` | Browser UI assets and HTML templates. The browser presents server-owned results; it must not duplicate recommendation, discovery, acquisition or import rules. |

## Clients

- `android/`: native Android client. Owns its UI, local playback/queue, device-side state and API integration; streams owned music directly from Navidrome.
  - Android layouts (`ui/theme/Palette.kt` `Layout`): each non-standard theme owns its own `<Theme>*.kt` files and is reached through one `is<Theme>()` branch in a shared control. **Gallery** (`Layout.Gallery`, eight palettes, spec `docs/GALLERY_THEME.md`, package `docs/design/gallery/`): `ui/common/GalleryKit.kt` (rules, type styles, prints, buttons, source switch, tabs, rows, state words, switch, tracker, banner), `ui/common/GalleryIcons.kt`, `ui/common/GalleryShell.kt` (dock bar with sliding marker, mini player, top bars, snackbar host and toast, sheet handle, the page-arrival clock `GalleryArrival`/`galleryArrive`, the dock's slide and `GalleryFlight`, which carries the mini cover's place so Now Playing can fly the cover between the dock and its print), `ui/theme/GalleryMotion.kt` (pure: section 8 motion values pinned to `tokens.json`, the staggered rise), fonts `res/font/fraunces_gallery*.ttf` and `manrope_gallery.ttf`. Screens follow as `Gallery<Screen>.kt` beside each screen: G2 Home is `ui/home/GalleryHome.kt` (arrangement with its own wordmark bar, so the shell draws no top bar on any Gallery page; the hero is a slideshow pager; reached from `HomeScreen`) and `GalleryHomeRules.kt` (pure: pager label, last-heard words, Radio plates and rows, library line); G3 Album, Artist and Genre are `ui/album/GalleryAlbum.kt`, `ui/artist/GalleryArtist.kt` and `ui/GalleryGenre.kt` (each reached from its screen by one `isGallery()` branch), with the pieces they share in `ui/common/GalleryPages.kt` (menu button, note, playing bars, captioned print, artist plate, read more) and the words in `ui/common/GalleryPagesRules.kt` (pure: catalogue lines, tabs, note); G4 Discover, Library and Search are `ui/discover/GalleryDiscover.kt` (head with Flow's one list switch and its list sheet, a two-column grid of tiles that carry the reason for each pick, Insights cards without lens headings, taste card and ranked bars), `ui/library/GalleryLibrary.kt` and `ui/search/GallerySearch.kt` (each reached from its screen by one `isGallery()` branch; the taste sheet and Insights page branch inside `TasteCard.kt` and `InsightsPage.kt`), with the words in `ui/common/GalleryListsRules.kt` (pure: date line, entry and taste lines, sort line, search detail); G5 Now Playing, Queue, Lyrics and Radio are `ui/player/GalleryNowPlaying.kt` (the full-screen page frame that rises and falls, the three views of one page sharing the seek line and transport, `GalleryPlayerRules` pure) and `ui/radio/GalleryRadio.kt` (stations, live radio, Heard; - `macos/`: native macOS client, split into audio, API/library, model and UI packages. Owns desktop presentation and local playback behavior.
- Both clients consume server contracts; neither is a second implementation of server recommendation or acquisition policy.

## Runtime and data boundaries

- The web process serves requests and runs only manual and read-triggered list refreshes. The separate worker process owns scheduled/background enrichment, insight refresh and the scheduled discovery and lens list refreshes (efficiency W3); while it is down, recommendation lists are not refreshed on schedule.
- SQLite application settings/authentication data and the dedicated Server V2 intelligence store persist under the configured data directory, outside the container image.
- Provider clients are called through `integrations/`; domain packages decide what to request and how returned data affects the product.
- Acquisition/import/cleanup are safety-critical: canonicalize paths under configured roots, reject traversal, symlink escapes and ambiguous targets, and never overwrite or remove unrelated files.

## Dependency rules

1. HTTP adapters call services/domain modules; they do not contain domain policy.
2. Domain modules use explicit provider and persistence dependencies rather than hidden app initialization.
3. Keep provider I/O in `integrations/`, recommendation policy in `recommendation/`, discovery policy in `discovery/`, and knowledge/enrichment state in `intelligence/`.
4. Preserve established API shapes, persistence semantics and client compatibility when changing ownership.
5. Do not resume size-only modularization. See `docs/DECISIONS.md` for binding decisions, `docs/TEST_PLAN.md` for verification, and `PROJECT_LOG.md` for implementation history.

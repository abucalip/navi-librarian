# Architecture

Last reviewed: 2026-11-17. This is a map of current module ownership, not a roadmap. GitHub `main` is authoritative.

## Server

| Module | Owns |
|---|---|
| `app/main.py`, `app/api/` | FastAPI assembly and HTTP adapters: request validation, authentication dependencies, response/status mapping and route registration. Keep business rules out of route handlers. |
| `app/security/` | Web-session authentication, login middleware, cookies and security boundaries. |
| `app/services/` | Application-lifetime services and background-worker coordination. `app/worker.py` starts worker-owned jobs; `app/worker_schedule.py` (efficiency W1) is its table-driven scheduler: one thread runs the due entries (`daily_maintenance`, then `insights_refresh`, then `similar_precompute`) one at a time and keeps each last run in the store's `meta` under `schedule:<name>` (a run that returns `NOT_READY` is not recorded and is retried after the entry's `retry_seconds`); it imports no job module, so `/api/diagnostics/runtime` reads those times (`schedule`) without loading worker code; auto fill and the metrics save keep their own threads; `library_enrich.py` and `insights_refresh.py` coordinate their respective loops. `similar_precompute.py` (efficiency W2) is the worker's daily similar-artist precompute: it builds its own owned index for the run (synchronously, dropped afterwards, no identity pass), runs `discovery/search/similar_precompute.run_precompute` from the stored cursor with the worker's stop event, and owns the artist-network arguments shared with the artist page (`network_kwargs`), so the worker imports no route module; the web process starts no precompute loop. `discovery_schedule.py` (efficiency W3) is the worker's second scheduler, on its own thread (`worker-schedule-discovery`) so the long precompute cannot delay it: `discovery_lists` (hourly: `refresh_stale_lists` over personal, classics, deep dives, new releases and the listening profile, none while automatic refill is off) and `lens_lists` (hourly: `lens_service._due`, then `refresh_exclusive`); it reads the librarian's helpers by attribute and does not import the legacy server; the web process starts no list refresh loop. `worker_heartbeat.py` (efficiency C3) is the worker's liveness stamp: a thread rewrites `DATA_DIR/worker.heartbeat` every 30 s only while `worker-schedule` and `worker-schedule-discovery` are alive, and `python -m app.services.worker_heartbeat` (the compose worker healthcheck) exits 1 when the stamp is over 5 minutes old; the web healthcheck uses the public `/api/auth/status`. `owned_prefetch.py` (efficiency K3 part 1) is the worker's `owned_prefetch` entry: one artist and one album in turn from the owned library (newest additions first, then by listens), each run through the page routes' own `artist_page` and `album_sections` with a worker-built network, so the provider rows it stores are the ones a first view would store, under the same keys; it imports no route module. It is off unless `OWNED_PREFETCH_BUDGETS` names daily per-provider caps. `prefetch_state.py` holds its budgets, request counting (`Spend`: a request past a cap, or to a provider not named, is refused before it is sent), per-day spent counts, cursors and coverage in the knowledge store's `meta` (`prefetch:spent`, `prefetch:cursor`, `prefetch:coverage`), and is read without worker code by `/api/diagnostics/runtime` (`prefetch`). Part 2 (efficiency K3) adds the album page's Deezer tracklist hook (cap `deezer`), Apple Music / Wikipedia description hook (caps `apple` and `wikipedia`, both needed) and year hook, each given to the worker's network only when its providers are named; `album_page_sources.py` owns those namespaces' loaders (HTTP `get` injected), store keys, TTLs and the rule that a refused or failed request is never stored, and both `app/api/metadata.py` (wrapped in `LayeredCache`) and the prefetch (read and write on the metadata store, since the worker does not attach `persistent_metadata`) use it, so the rows match by construction (`tests/test_album_page_sources.py` checks it); it imports no route module. The same module also owns the album year (MusicBrainz request counted through the cap), album links and artist image loaders; `owned_prefetch.entity_extras` runs the links and the image outside the page builders, and, only when `OWNED_PREFETCH_BUDGETS` names a `reviews` cap (none by default), the album reviews. `album_review_sources.py` owns the review outlets (Pitchfork, the Guardian with `GUARDIAN_API_KEY`, the WordPress outlets; HTTP `get` and store `read`/`write` injected), their store keys (`album-review-source:v1`, `album-reviews:v1`, the K4 failure marks), TTLs and storing rules; `app/api/metadata.py` asks them in parallel under its deadline with K2 stale serving and stores the list, and the prefetch asks them one after another through its cap and stores outlet answers only (its outlet set can lack the Guardian; a cap refusal marks nothing); it imports no route module. `runtime_metrics.py` holds the in-process counters (provider requests by provider and outcome class, gate waits, store opens and statements by verb; no URLs or identifiers), fed by a process-wide patch of `httpx.Client.send`/`AsyncClient.send` and `urllib.request.OpenerDirector.open` (`count_all_httpx`, installed at startup; `MeteredClient` is the same count without the patch), by the observer hooks in `integrations/provider_gate.py` and `intelligence/store/db.py`, and read at `GET /api/diagnostics/runtime` (`app/api/diagnostics.py`); providers are named from a fixed host table (Last.fm's API host `ws.audioscrobbler.com` included; the album review outlets' hosts together as `reviews`), and the Navidrome client labels its requests `navidrome` (the shared client and a caller's own `client_factory` client alike) through a request event hook (the `metrics_provider` request extension), since Navidrome's host is configured; the worker saves its snapshot to the store's `meta` every 5 minutes. `layered_cache.py` is the metadata routes' cache (efficiency P4): `LayeredCache` keeps a bounded LRU per namespace (2,000 entries by default), reads `persistent_metadata` when given a store key, and runs the caller's loader under single-flight, so concurrent identical requests make one provider call; the loader's `Loaded` answer sets its memory TTL (or none) and whether it is stored. With `max_stale` (efficiency K2, opt-in per call: album reviews, album links, the Apple album page address) a stored value past its TTL but inside its maximum staleness (70 days) is answered at once, kept in memory for at most 10 minutes, and refreshed by one background run of the same loader; with `stale_fetched_at` (album reviews and album links) such a dict answer is a copy carrying `fetched_at` (UTC ISO 8601, the row's store time), never stored; ages come from `MetadataCache.get_with_age` through `persistent_metadata.read_with_age`, attached in `app/main.py`. `stale_refresh.py` (efficiency K2) runs those refreshes on its own two-thread pool, one per key, at most 32 pending (more are dropped and the stale value stays); a failed refresh writes nothing. K2 part 2 applies the same rule to the artist and album pages' provider rows in the discovery search cache (`discovery/search/cache.py::read_or_revalidate`: MusicBrainz artist lookup, studio albums and the seed artist's tags, Last.fm album lists, ListenBrainz and Last.fm top songs, Discogs styles, tracklists): a row past its TTL and under 10 times it (an empty answer: 1 h TTL, 10 h) is served and refreshed on `stale_refresh.DISCOVERY_REFRESHER`, a second pool of the same size, handed to the page network only by `app/api/search.py::artist_network_for`; the worker precompute and the search and genre pages keep today's expiry, and candidates' tag lookups are not served stale. Each page section job runs under `cache.run_noting_stale`, so a section built from such a stale row states `fetched_at` (the oldest one's store time; the identity lookup does not count). The review outlets' own answers (`album-review-source`) use it directly from `app/api/metadata.py`, and an answer built from a stale input is never stored as fresh. `negative_marks.py` (efficiency K4, K5) writes and checks short-lived dated marks (`{"negative": true, "at"}`) in the metadata store under their own keys, never under an answer's key: K4 marks a review outlet that failed or timed out for an album (`album-review-source-failed:v1:*`, 1 h; the outlet is skipped and the list stays partial), and K5 marks a definitive Deezer or Apple no-match (`album-no-match:v1:{deezer|apple}:*`, 1 h, written in `album_page_sources.py` only after a provider answer, never after a failure or refusal). K6 adds a found Deezer album page under its own key (`album-deezer-url:v1:*`, 7 days, read by `load_album_links` so an incomplete set does not re-ask Deezer) and a Wikipedia no-article mark (`album-no-match:v1:wikipedia:*`, 1 h, written only when the search answered and no article matched). The MusicBrainz year cache those routes import (`integrations/musicbrainz/album_year.py::year_cache`) is a separate LRU dict of 2,000 pairs, since `integrations/` does not import `app/`. |

## Runtime and data boundaries

- The web process serves requests and runs only manual and read-triggered list refreshes. The separate worker process owns scheduled/background enrichment, insight refresh and the scheduled discovery and lens list refreshes (efficiency W3); while it is down, recommendation lists are not refreshed on schedule.
- SQLite application settings/authentication data and the dedicated Server V2 intelligence store persist under the configured data directory, outside the container image.
- Provider clients are called through `integrations/`; domain packages decide what to request and how returned data affects the product.
- Acquisition/import/cleanup are safety-critical: canonicalize paths under configured roots, reject traversal, symlink escapes and ambiguous targets, and never overwrite or remove unrelated files.

## Dependency rules

1. HTTP adapters call services/domain modules; they do not contain domain policy.
2. Domain modules use explicit provider and persistence dependencies rather than hidden app initialization.
3. Keep provider I/O in `integrations/`, recommendation policy in `recommendation/`, discovery policy in `discovery/`, and knowledge/enrichment state in `intelligence/`.
4. Preserve established API shapes, persistence semantics and client compatibility when changing ownership.
5. Do not resume size-only modularization. See `docs/DECISIONS.md` for binding decisions, `docs/TEST_PLAN.md` for verification, and `PROJECT_LOG.md` for implementation history.

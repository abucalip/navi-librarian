# v0.2 Improvement Backlog: Lessons from DroppedNeedle

**Status:** Planning document; recommendations are not implemented commitments.  
**Target:** Navidrome Librarian v0.2  
**Reference reviewed:** [DroppedNeedle](https://github.com/DroppedNeedle/DroppedNeedle), with selected matching, acquisition, quality, discovery, caching, and test files inspected on 2026-10-12.

## 1. Purpose and boundaries

Use useful ideas observed in DroppedNeedle to improve Librarian's reliability and maintainability. Borrow design principles and independently implement only what fits Librarian's needs. This document is a backlog and review guide, not a mandate to reproduce DroppedNeedle's architecture.

### Librarian's scope remains unchanged

Librarian is a focused bridge between an existing Navidrome library and slskd acquisition, with music recommendations informed by both library contents and listening taste.

- Navidrome remains the source of truth for the user's music library.
- slskd remains the acquisition integration.
- Recommendations continue to use Librarian's existing library-aware and taste-aware logic and configured metadata/listening providers.
- Preserve the existing Python, FastAPI, and MCP interfaces unless concrete evidence justifies a narrowly scoped change.
- Do not grow Librarian into a full music-library manager, independent download platform, audio-tagging suite, or replacement for Navidrome/slskd.

## 2. Non-negotiable engineering principles

### Smoothness and stability come before architectural ambition

The user's experience of DroppedNeedle has often been painfully slow and buggy. Its code can provide useful patterns, but its architecture or implementation must not be treated as automatically superior.

For every proposed change:

1. State the user-visible problem and expected benefit.
2. Identify the current root cause before changing code.
3. Prefer a focused improvement over a broad rewrite.
4. Establish a baseline for latency, request counts, error rate, and relevant behavior where practical.
5. Add regression tests before or alongside the fix.
6. Avoid new background work, provider calls, polling, or synchronous filesystem work on UI request paths unless necessary.
7. Keep external metadata optional: provider failure should not break core discovery or the acquisition UI.
8. Verify the real UI/API behavior, not just successful compilation.
9. Retain a straightforward fallback and useful diagnostics when external services fail.
10. Do not trade responsiveness or predictable behavior for more layers, abstractions, or features without measured justification.

### Split responsibilities into focused Python modules—incrementally

DroppedNeedle demonstrates a useful direction: focused modules for matching, quality evaluation, acquisition decisions, orchestration, discovery, and persistence are easier to reason about than one oversized module.

Librarian should move in this direction, but **module splitting is a means to clarify ownership, not an end in itself**.

- Keep API handlers thin and keep domain behavior outside the web layer.
- Reuse existing recommendation and acquisition logic; do not duplicate it in FastAPI routes.
- Extract a module when it has a clear responsibility, stable inputs/outputs, and meaningful tests.
- Keep related logic together where splitting would only create extra indirection.
- Preserve public MCP tool names and response compatibility.
- Avoid introducing a large framework, dependency-injection system, event bus, or many layers merely to imitate another project.
- Refactor in small steps with tests proving behavior remains unchanged.

## 3. Prioritized improvement backlog

Priorities are provisional. Reassess against current code and tests before each implementation. Do not start every item at once.

### P0 — Acquisition completion evidence and diagnostics

**Why:** Librarian has repeatedly shown a completed-transfer state while failing to recognize a completed folder that appears to contain the expected files. This is a concrete reliability problem and the best first target.

DroppedNeedle references:
- `backend/services/native/album_evidence_engine.py`
- `backend/services/native/album_matcher.py`
- `backend/services/native/download_orchestrator.py`
- `backend/tests/services/native/test_acquisition_cleanup_service.py`

Ideas to adapt:
- Evaluate completion using explicit, inspectable evidence instead of a single vague status.
- Keep transfer completion, folder discovery, file completeness, identity matching, and import readiness as distinct conditions.
- Return actionable reasons when completion cannot be confirmed.
- Normalize filenames and paths consistently (including Unicode normalization, case folding where appropriate, and slash differences) while preserving safe path boundaries.
- Compare unique expected audio filenames and observed files; account for duplicate names, collision suffixes, and available size evidence without assuming size alone proves identity.
- Exclude artwork, cue sheets, playlists, logs, and other non-audio files from track counts.
- Avoid treating a temporarily unavailable folder as permanently failed; use bounded, observable retries rather than rapid polling or indefinite waiting.

Acceptance criteria:
- Regression fixtures reproduce the reported failure and related path/filename edge cases.
- A complete, unambiguous acquisition is recognized when its files become available.
- Missing, incomplete, ambiguous, or unsafe folders are not imported.
- Diagnostics explain which condition failed.
- Waiting/retry behavior is bounded and does not make the UI feel stuck.
- Existing import and acquisition behavior remains covered by regression tests.

### P0 — Safe, explicit acquisition lifecycle boundaries

DroppedNeedle references:
- `backend/services/native/acquisition/`
- `backend/services/native/acquisition_cleanup_service.py`
- `backend/api/v1/routes/downloads_search.py`

Potential responsibility boundaries (module names are illustrative, not a required design):
- Candidate matching and selection.
- Quality-profile evaluation.
- Transfer progress and stalled-transfer detection.
- Completed-folder resolution.
- Import/finalization.
- Cancellation and cleanup.

Start with the smallest extraction that makes the current completion bug easier to test. Do not split the entire acquisition implementation in one refactor.

Safety requirements:
- Keep dismissal/deletion explicit and scoped to the intended album's approved directory.
- Validate resolved paths and ownership before destructive operations.
- Do not delete files based only on a fuzzy album-name match.
- Keep cleanup idempotent where possible and return clear conflicts when safe cleanup cannot be established.
- Preserve the existing Get behavior: request the album without unnecessary navigation, show the requested state, and surface it in Acquisitions.
- Keep cancellation, dismissal, transfer failure, and successful import as distinct states.

Acceptance criteria:
- Unit tests cover each extracted boundary.
- Tests prove intended files are affected and unrelated files are untouched.
- API and UI behavior are tested where applicable.
- The refactor does not duplicate domain logic or change MCP contracts unintentionally.

### P1 — Consistent quality evaluation

DroppedNeedle reference:
- `backend/services/native/quality_tiers.py`

Ideas to adapt:
- Use one clearly owned quality-classification function for candidate evaluation and any later acquisition checks that need the same decision.
- Keep Librarian's existing user-facing profiles: MP3 320, MP3 193–319, MP3 192, and FLAC CD.
- Distinguish supported audio formats from arbitrary files returned with a remote folder.
- Report why a candidate was rejected (unsupported format, profile mismatch, missing expected tracks, or insufficient evidence).
- Do not assume that file extension or reported bitrate alone proves actual audio quality.
- Avoid expensive media probing for every candidate unless it is needed to resolve a real ambiguity.

Acceptance criteria:
- Tests pin profile boundaries and supported formats.
- Non-audio extras do not count as tracks.
- Candidate selection and downstream validation use consistent rules.
- Quality evaluation does not materially slow browsing or acquisition search.

### P1 — Recommendation pipeline clarity and identity safety

DroppedNeedle references:
- `backend/api/v1/routes/discover.py`
- `backend/services/discover/`
- `backend/services/native/artist_identity_reconciliation_service.py`

Ideas to adapt:
- Keep candidate discovery, artist/album identity resolution, eligibility filtering, category assignment, ranking, and diversity constraints conceptually distinct.
- Make it possible to explain why a candidate was excluded or ranked in a category.
- Strengthen artist identity and library-ownership checks before final selection.
- Protect existing release-type filtering and prevent recommendations for albums already in the library.
- Preserve variety across Librarian's established categories and avoid letting one provider or popularity source dominate.
- Keep provider-specific code behind the existing integration boundaries and handle missing/failed provider results gracefully.

Do not import DroppedNeedle's recommendation sources, popularity assumptions, or full discovery architecture without evidence they improve Librarian's personalized results.

Acceptance criteria:
- Tests cover owned-album exclusion, artist identity ambiguity, release eligibility, category targets, and diversity.
- Diagnostics explain shortfalls without exposing excessive raw provider data to the UI.
- Recommendation latency and provider-call counts do not regress materially.

### P2 — Metadata and artwork caching review

DroppedNeedle reference:
- `backend/infrastructure/cache/disk_cache.py`
- `backend/infrastructure/audio/artwork_processor.py`

First audit Librarian's existing caches and request flow; do not add a second cache abstraction by default.

Potential improvements:
- Deduplicate concurrent requests for the same metadata or artwork.
- Choose cache lifetimes appropriate to the data.
- Handle stale or invalidated results so slow lookups do not overwrite newer state.
- Keep cache size and filesystem access bounded.
- Ensure artwork and biography failures do not block the core page or discovery result.

Acceptance criteria:
- Measure request counts and page latency before and after.
- Test expiry, invalidation, concurrent lookups, and provider failure as relevant.
- Keep the UI responsive on cache misses and external-service outages.

### Continuous — Regression tests and diagnostics

DroppedNeedle reference:
- `backend/tests/services/native/test_acquisition_cleanup_service.py`
- `backend/tests/infrastructure/`
- `backend/tests/routes/`

Adopt the testing approach, not necessarily the same directory structure or tooling.

Build reusable fixtures for:
- Completed transfer with delayed folder visibility.
- Completed folder with Unicode-normalized or differently separated paths.
- Expected tracks plus non-audio extras.
- Missing tracks and ambiguous folder candidates.
- Similar album/artist names.
- Unsupported formats and quality-profile boundaries.
- Provider timeouts, missing metadata, and stale results.
- Cleanup attempts that target a wrong or out-of-bound path.

For destructive behavior, test both the intended outcome and the safety invariant that unrelated files remain untouched.

## 4. Performance and stability guardrails

Use these as review questions for every v0.2 change:

- Does it add external requests, repeated polling, or background jobs? If so, why are they necessary and how are they bounded?
- Does a cache miss or provider timeout block a UI/API response?
- Is there a timeout, cancellation path, and useful error state?
- Can repeated requests trigger duplicate downloads or duplicate work?
- Does the feature work when optional metadata providers are unavailable?
- Are resource use and latency measured where the change could affect them?
- Is the code simpler to debug after the change?
- Can the feature be disabled or reverted without losing user data?
- Are path validation and destructive-operation safety preserved?

Prefer fewer reliable operations over a more elaborate pipeline. Add observability that helps diagnose real failures, but avoid noisy logs and excessive diagnostics payloads.

## 6. Suggested v0.2 order

1. Re-inspect the active branch, current acquisition code, and existing tests.
2. Reproduce the completed-folder recognition failure in a deterministic test.
3. Add precise completion diagnostics and fix the root cause with the smallest change.
4. Verify cleanup and dismissal safety with positive and negative filesystem tests.
5. Review and unify quality evaluation where duplication actually exists.
6. Improve recommendation identity/diversity diagnostics only after auditing current behavior.
7. Review cache performance using measurements, then make targeted changes if justified.
8. Run relevant tests, the full suite where feasible, syntax/build checks, and UI/API checks; inspect the final diff.
9. Update project status and log with exact implementation and verification state.

Do not treat the list as a commitment to ship every item in v0.2. Prioritize proven user value and stability over feature count.

## 7. Definition of done for each adopted idea

An item is complete only when:
- The current implementation and root cause were inspected.
- Acceptance criteria were defined before coding.
- Focused regression tests were added or updated.
- Relevant tests and broader checks were run where feasible.
- Performance and UI/API behavior were verified when applicable.
- The diff was reviewed for unrelated changes.
- Documentation records what is implemented, tested, merged, and deployed separately.
- Remaining limitations are explicit.

**Current state:** This document records proposed improvements only. No application code changes or performance claims are implied.
